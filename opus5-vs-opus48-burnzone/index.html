A Kriya Lab · 27 July 2026

Opus 5
vs Opus 4.8

The successor arrives at exactly the same price — $5/$25 per MTok. No premium to justify, no tier to trade off. So the only question left is the honest one: does it actually build better software?

Same four Kriya SDLC roles, same BurnZone brownfield, same answer keys as the Fable lab · real headless runs on a Claude Max plan · served-model verified from billing telemetry · generated code discarded.

The question

When the upgrade is free,
what is there left to decide?

Every prior lab in this notebook asked a price question. Sonnet 5 was cheaper — was it good enough? Fable 5 was 2× dearer — was it worth it? Opus 5 is neither. It lands on Opus 4.8's exact rate card.

So the question changes shape: not "is it worth the premium" but "is the extra token volume worth it" — because a model that thinks by default spends more even at an identical rate.

And the answer turned out to depend entirely on what kind of deliverable the role produces.

The test bed

A real brownfield,
with real holes in it.

BurnZone is a live multi-tenant gym-SaaS — Express + TypeScript + Postgres, JWT + RBAC, ~712 real member accounts in production. Not a benchmark fixture. The tasks come from its actual Kriya Stage-C dossier and its actual fix commit 7f7b986.

The four roles

  • A · Security capture — 5 seeded-real defects, 2 of them CRITICAL, plus two planted false-positive traps
  • B · Producer-code — a production bug with one correct minimal fix
  • C · Architect — Stage-0 strangler plan, 16-item rubric
  • D · Gate-verifier — a planted fail-open; correct answer is VETO

Why reuse the Fable suite

  • Same prompts, same keys, same default effort as lab #3 — so Opus 5 lands directly comparable to Fable 5
  • Tasks A and D are security-flavoured — precisely where Fable's classifiers declined
  • The keys are grounded in a shipped commit, not an opinion
Method · what makes this auditable

The model doesn't get to
tell us who it is.

Measurement — automated

  • Both arms run the identical prompt file, in parallel, per task
  • Served model, tokens, cost and duration read from Claude Code's modelUsage billing telemetry
  • Costs re-normalized to official published rates, never the internal cost table
  • Only distilled metrics enter the repo — generated code is discarded

Judgement — explicit, in-repo

  • Objective keys written before the runs, from the real dossier
  • Every extra finding re-checked against the pasted source before being credited
  • False-positive traps scored in both directions
  • scores.json ships beside the results so the grading is reviewable

Models misreport their own identity — a claude-sonnet-5 run once insisted it was 4.6. Billing telemetry is the only ground truth.

The rubric saturates — both arms max it. But one rubric item had been only implicitly satisfied by every arm in every prior lab: pinning a no-500 invariant. Opus 5 is the first to make it explicit, as invariant I6 · Error taxonomy.

Opus 5 · off-rubric depth

  • INTENDED/OBSERVED/SUSPECT golden classification — SUSPECT goldens carry a companion red test, so the two known CRITICALs enter the net as red tests and can never be canonized
  • A mutation-score merge gate on auth middleware — because assertion count is gameable and mutation score isn't
  • 90-day traffic window for billing and cron routes: monthly jobs are invisible in a 30-day window
  • Hard caps as forcing functions — UNDECIDED ≤ 10%, FINISH ≤ 12 "so triage doesn't become a roadmap"

Opus 4.8 · its own standout

  • Authors the AuthZ matrix against intended policy, not observed behavior — so freezing the net can't enshrine the live auth bug
  • stale_flag_gate with mandatory flag expires_at
  • Reached 16/16 in one third the tokens

What Opus 5 ranked above the planted bug

That the authorization decision keys off the attacker-supplied request string rather than the role row the database already resolved — so the deny-list isn't closed, only narrowed.

"CRIT-2 is not closed; it is narrowed to attackers who don't read the deny-list."

Plus: non-atomic audit write leaving unlogged role changes reachable, an enumeration of prerequisites the patch assumes but never establishes, and a "required to flip this to PASS" checklist.

The verdict

Buy the depth where the
deliverable is depth.

Opus 5 wins where output is an enumeration

  • Security audit — 15 defects vs 6, zero FPs either way
  • Gate verify — 6 findings vs 3, at only 1.32×
  • Write-once architecture — closed the no-500 gap every prior arm left open
  • It never declined — unlike Fable 5, on the exact same prompts

Opus 4.8 holds where output is one answer

  • Routine build — same correct fix, 4/4 invariants, 1.5× cheaper
  • Repeated design — 16/16 at a third the tokens
  • Extra reasoning has nowhere to go when the answer space is a single minimal patch

Neither model missed a keyed defect. This entire verdict rests on depth beyond the key — which is a judgement call, made explicitly and in-repo rather than hidden in a score.

What this lab does not prove

The honest margins.

  • Single run per task. The 15-vs-6 and 6-vs-3 margins are one sample each. Signal, not a benchmark.
  • The keys saturated. All four tasks were ceiling-tied, so the entire recommendation rests on grader-assessed depth beyond the key.
  • Effort was equal, not thinking-matched. Both ran Claude Code defaults — but Opus 5 thinks by default and 4.8 doesn't, which is most of the 1.97× token gap. This is a real-world default-vs-default result, not a controlled reasoning comparison.
  • Severity calibration is not a win here. Opus 5 diverged from the key in both directions on Task A — it ranked a seeded CRITICAL as HIGH.
  • The source was an excerpt. Opus 5 self-flagged two of its own findings as unverifiable from it; those were credited only after the grader checked the source.
  • Graded by the author against real-commit keys — not a blind expert panel.
Close

A free upgrade still has
a bill attached.

Opus 5 costs the same per token and is measurably deeper. But it spends roughly twice as many tokens by default, so "same price" is a rate, not an invoice. The routing question survives the price parity — it just moves from the rate card to the workload.

Route it where the deliverable is the enumeration. Keep 4.8 where the deliverable is a single correct answer. And keep verifying which model actually served you.
